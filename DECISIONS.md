# DECISIONS — every important choice, with numbers

## D1. Rendering method — own WebGL2 renderer (chosen) vs Canvas 2D
Bench: `tools/bench/render-bench.html` (256×256 tile map, 1,500 moving 16×16 sprites, 640×360 target, 300 frames each, headless Chromium 153, **software GL (SwiftShader)**, 4 cores). Milliseconds per frame, CPU side, forced sync:

| approach | zoom ×1 avg / p95 | whole map (zoom 0.31) avg / p95 | zoom ×3 avg |
|---|---|---|---|
| Canvas 2D, one drawImage per tile | 22.1 / 30.1 | 164.8 / 253.2 | 1.9 |
| Canvas 2D, 32×32-tile chunk cache | 0.42 / 0.6 | 2.9 / 3.5 | 0.23 |
| **WebGL2, tile shader + instanced sprites** | 4.3 / 5.1 | 19.7 / 23.7 | 2.6 |

Reading: naive Canvas 2D fails (22 ms at ×1). Chunked Canvas 2D is the fastest *on a software rasteriser*, but cannot do what the art direction needs without re-baking chunks: per-pixel palette indexing (kingdom ramps, tone shifts), animated water/lava in the shader, autotile blending, light accumulation and day/night grading. WebGL2 does all of that in one pass, already holds 60 fps on software GL at ×1 (4.3 ms), and on any real GPU the fragment cost — the whole difference here — drops to well under a millisecond. **Decision: own WebGL2 renderer, no library** (a rendering library would add weight and hide the indexed-palette pipeline). The software-GL numbers are kept as the pessimistic reference in REPORT.md.
A third option, a rendering library (PixiJS-like), was not benchmarked because rule 3 forbids downloading anything in this environment and no copy was available offline; the two measured approaches bound the decision.

## D2. Libraries
Runtime: **none**. Development: Node 22 (runs the tools), Playwright 1.63.0 with its Chromium (pre-installed test tool; drives real keyboard/mouse events). See PROVENANCE.md.

## D3. Language and delivery
Plain JavaScript, classic scripts concatenated by `tools/build.js` into `game/dustcrown.js`; assets embedded as a script (`game/assets.js`) so that `game/index.html` opens from `file://` (no fetch, no module, no CORS problem). TypeScript rejected: it needs a compiler install and the project has no dependency otherwise.
Simulation runs in a **Blob Worker** built from the simulation bundle's own source text (works on `file://` and static hosts, no special header; SharedArrayBuffer deliberately not used because it requires COOP/COEP headers). Snapshots are posted with transferable typed arrays.

## D4. Internal resolution, tile size, scaling
| candidate | 720p | 1080p | 1440p | 4K | integer everywhere |
|---|---|---|---|---|---|
| 480×270 | ×2.67 | ×4 | ×5.33 | ×8 | no |
| **640×360** | ×2 | ×3 | ×4 | ×6 | **yes** |
| 960×540 | ×1.33 | ×2 | ×2.67 | ×4 | no |

**Decision: 640×360**, the only candidate that scales by an integer on all four targets. Tile sizes dividing both 640 and 360: 8, 10, 20, 40 → **8 px** (80×45 tiles at zoom ×1). Apparent size of a unit (17 px tall body in a 24×24 cell) at zoom ×1: 34 px at 720p, 51 px at 1080p, 68 px at 1440p, 102 px at 4K. "Fill" mode uses the largest integer scale and extends the internal width/height to cover the window (no blur, no bars). Other windows letterbox to the nearest integer scale.

## D5. Sprite sizes
First bench at 16×16 for people (sheet `shots/step1-bench-people-a.png`, first runs): head 5 px wide, limbs and tools unreadable. Re-baked at 24×24: face, hair, arms, legs and tools read. **Decision: people 24×24** (body ≈ 11×17). Full table in STYLE.md.

## D6. Asset pipelines per category (bench sheet `shots/step1-bench-pipelines.png`, looked at ×4)
Subjects made twice: human (A: SDF rig bake / B: painted grid), deer (A / B), grass (C: rules, 32×32 seamless / B: three painted 8×8 tiles), oak (C: 2D cluster rules / A: SDF blobs), house (A: SDF kit with material patterns / B: painted grid).

| category | observed | decision |
|---|---|---|
| peoples, animals, monsters | B is the crispest single frame (clean face, limbs); A is a little softer but gives 4 directions, 50+ coherent frames and all job/age variants from one rig. Painting 2 peoples × 16 variants × ~200 frames by hand is out of reach and would flicker. | **A (SDF rig) + explicit pixel decals (eyes, tusks) + D patches on key poses** |
| trees, flora, rocks | C clusters read as foliage with a clear light side; A blobs look like balloons, pattern noise is random. | **C + D** |
| terrain | C gives 16 non-repeating variants and calm masses; B repeats visibly at 3 tiles. | **C + D**, 47-case blob transitions generated by C |
| buildings | A gives a correct roof/wall light, patterns (shingles, timber), free construction stages (clip plane) and ruins; B is crisp but 72+ sprites by hand cannot stay consistent. | **A (SDF kit + material patterns) + D** |
| icons, font, UI | — | **B** (painted grids) |
| effects | — | **C** (frame generators) + runtime particles; a few **B** |

Unification: every pipeline writes palette indices only, uses the same light vector and the same `outline()` function from `tools/lib/sdf.js`.

## D7. Asset delivery: baked atlases (chosen) vs generated at load
Baking the people atlas takes minutes of CPU (ray-marched SDF), so generation at load is impossible within the 5 s budget. **Decision: bake offline with the tools, ship indexed atlases** (1 byte per pixel, run-length encoded, base64 in `game/assets.js`, decoded synchronously — no image decode, no canvas). PNG copies are written to `assets/` only for looking. Size measured in REPORT.md.

## D8. Simulation architecture
Column-oriented typed arrays, fixed capacity (8,192 entities), 10 ticks/s, deterministic RNG (xoshiro128**), utility AI evaluated every 8 ticks per unit in staggered groups, movement every tick. See ARCHITECTURE.md.

## D9. Pathfinding
Alternatives: (a) per-unit A* on the tile grid for every trip; (b) shared flow fields per destination; (c) hierarchical (cluster graph). Decision: **region labels** (connected walkable components, recomputed on terrain change) for O(1) reachability + **bounded A*** (binary heap on typed arrays, ≤ 4,000 expansions) for individual trips ≤ 48 tiles + **shared flow fields** (Dijkstra over the whole region, cached LRU ×48) for many-to-one trips (armies, caravans, returning home to a town centre). Measured numbers are added in step 4/5.

## D10. Time scale
10 ticks/s; day 300 ticks; year 1,200 ticks (4 days = 4 seasons). At ×50 the worker needs 500 ticks/s → tick budget 2 ms; if a tick takes longer the worker lowers the effective speed and the UI shows the real one (stable, no spiral of death).

## D11. Saves
Whole state serialised by the worker into one binary buffer (typed arrays + JSON header), stored in IndexedDB (slots + autosave) with a localStorage index; export/import as a `.aeon` file. Identity test: save → load → save must give byte-identical buffers, and the reloaded world must then evolve identically for 500 ticks.
